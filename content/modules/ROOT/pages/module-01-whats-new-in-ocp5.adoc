== Start here: Log in to OpenShift

Open the Showroom *Terminal* tab and authenticate using your assigned workshop credentials *before running any other +oc+ commands*:

[source,bash,subs="attributes+",role=execute]
----
oc login --server={openshift_api_url} --username={user} --password='{password}' --insecure-skip-tls-verify
oc whoami
----

Verify that +oc whoami+ returns {user}. This is a disposable lab environment: the +`-p`+ option can expose your password in shell history and process listings. Do not reuse this password on a personal or production cluster.


Deploy the National Parks frontend, Python API and MongoDB 8 in your existing workshop project. The MongoDB Service contains a deliberately incorrect port. Use Lightspeed 2.0.1 Troubleshooting to diagnose the failure, approve a narrowly scoped MCP repair, and verify the change before loading park data. Leave Argo CD, Gitea and other workshop workloads alone.

This is a *25–30-minute, console-first workshop* using *OpenShift Lightspeed 2.0*. The guided walkthrough targets 28 minutes, with up to 2 minutes for transitions.

These timings assume your instructor has already verified image pulls, the Python build, student permissions, Lightspeed MCP read/write tools, tool approval and Argo CD/Gitea isolation. If a prerequisite fails, troubleshoot it separately rather than counting it against the lab. Lightspeed investigates the fault and offers a scoped repair when the real approval control is available; a manual console recovery is provided otherwise.

== Mission 4: Ask Lightspeed to find the fault (4 minutes)

The Python API runs, but the park data is missing. Your job is to use live OpenShift evidence to find the broken connection. Start with the two resources that connect the application to MongoDB rather than investigating the whole cluster.

. Open *OpenShift Lightspeed* -> *Troubleshooting*.
+
image::module01-s09k-lightspeed-mode.png[Select Lightspeed Troubleshooting, width=850]
. Ask this short question:
+
[source,text,subs="attributes+"]
----
My National Parks app cannot load park data.
In {user}-demo, compare only the mongodb-nationalparks Service and Deployment
using resources_get. What's wrong? Don't change anything.
----
. Look at the *live port values* in the reply. The MongoDB container listens on `27017`, but the Service sends traffic to `27018`. That is why the application cannot reach MongoDB. Don't change anything yet.
+
image::module01-s07-lightspeed-root-cause.png[Live Lightspeed 2 diagnosis showing MongoDB Service targetPort 27018 versus Pod containerPort 27017, width=900]

[TIP]
====
Keeping the question focused on one Service and one Deployment makes the diagnosis easier to understand and avoids unnecessary cluster-wide investigation. If Lightspeed cannot read these resources, ask the instructor; do not try to grant permissions or switch off safety checks.
====

*Checkpoint 4:* Lightspeed identifies the mismatch: `targetPort: 27018` versus `containerPort: 27017`. You know which field is wrong.

== Mission 5: Repair MongoDB with Lightspeed (3 minutes)

You have found the fault. Now ask Lightspeed for one small change, review it and verify whether it really happened. A message saying "fixed" is not proof, and a sentence asking for approval is not the actual approval control.

. In the Showroom *Terminal*, capture the broken Service setting:
+
[source,bash,subs="attributes+"]
----
oc get svc mongodb-nationalparks -n {user}-demo \
  -o jsonpath='{.spec.ports[0].port}{" -> "}{.spec.ports[0].targetPort}{"\n"}'
----
+
Expected: `27017 -> 27018`. If the result is already `27017 -> 27017` or `27017 -> mongodb`, the Service is already correctly routed; ask the instructor to reset the fault rather than making an unnecessary change.
. In the *same Lightspeed conversation*, ask:
+
[source,text,subs="attributes+"]
----
Use resources_create_or_update to fix only the mongodb-nationalparks
Service in {user}-demo: set targetPort to 27017; keep all else unchanged.
Submit the tool call for my approval. Don't bypass approval.
Verify the Service after the approved change.
----
. Check for a separate *tool approval request* showing `resources_create_or_update` for `Service/mongodb-nationalparks` in *{user}-demo*. Review the proposed change. Approve *only* if the Service's `targetPort` changes to the numeric value `27017` and other fields remain untouched. The backend can issue the request even when the model mistakenly says it cannot. If Lightspeed only asks you to type `APPROVE` in chat, *do not treat that as a tool approval*; use the manual recovery below if no separate approval control appears.
. Whether Lightspeed reports success or not, check the actual Service again:
+
[source,bash,subs="attributes+"]
----
oc get svc mongodb-nationalparks -n {user}-demo \
  -o jsonpath='{.spec.ports[0].port}{" -> "}{.spec.ports[0].targetPort}{"\n"}'
----
+
Expected after repair:
+
[source,text]
----
27017 -> 27017
----

[IMPORTANT]
.How to interpret the result
====
A verified `27017 -> 27017` means the Service was repaired. It does *not* prove that the approval mechanism worked. If the Service changed **without you seeing and approving a separate tool request**, tell your instructor. Do not claim that you completed an approved AI repair or repeat that behaviour on other workloads. Never modify Secrets, Deployments or anything outside your own project.
====

=== Manual repair if approval is unavailable

If Lightspeed cannot show the actual approval control, stop the AI write attempt and repair the single Service field yourself:

. Open *Networking* -> *Services* -> `mongodb-nationalparks` -> *YAML* -> *Edit*. Set only `spec.ports[0].targetPort` to numeric `27017`, then save:
+
[source,yaml]
----
ports:
  - name: mongodb
    port: 27017
    targetPort: 27017
    protocol: TCP
----
+
image::module01-s07a-lightspeed-fix-console.png[Manual recovery: change only the MongoDB Service targetPort, width=850]
+
Alternatively, the student-terminal patch changes just that field:
+
[source,bash,subs="attributes+"]
----
oc patch svc mongodb-nationalparks -n {user}-demo \
  --type=json \
  -p='[{"op":"replace","path":"/spec/ports/0/targetPort","value":27017}]'
----
+
image::module01-s07b-lightspeed-fix-oc.png[Manual recovery: scoped oc patch command, width=850]
+
Repeat the Service check above; do not proceed until it returns `27017 -> 27017`.

| Cannot see `{user}-demo` | Sign in as your own student account.
| Python build fails | Open *Builds* -> *Logs* and inspect the error.
| MongoDB Pod not Ready | Check the Secret name, bootstrap ConfigMap and Pod events.
| Backend cannot retrieve data in Mission 3 | Expected. Investigate with Lightspeed before fixing the MongoDB Service.
| Lightspeed cannot inspect resources | Check the student's namespace and permissions. Use the short Service-and-Deployment question; notify the instructor if a safety inspection fails.
| Lightspeed says it cannot show approval | Stop the AI write path; use the manual Service repair and tell the instructor. Do not accept approval expressed only in chat text.
| Backend still cannot connect after Mission 5 | Confirm the MongoDB Service `port` and numeric `targetPort` are both `27017`, and inspect backend logs.
| API returns records but map is blank | Check the `parksmap-discovery` ServiceAccount and the `type=parksmap-backend` label on `Service/nationalparks`.
