== Start here: Log in to OpenShift

Open the Showroom *Terminal* tab and authenticate using your assigned workshop credentials *before running any other +oc+ commands*:

[source,bash,subs="attributes+",role=execute]
----
oc login --server={openshift_api_url} --username={user} --password='{password}' --insecure-skip-tls-verify
oc whoami
----

Verify that +oc whoami+ returns {user}. This is a disposable lab environment: the +`-p`+ option can expose your password in shell history and process listings. Do not reuse this password on a personal or production cluster.


Deploy the National Parks frontend, Python API and MongoDB 8 in your existing workshop project. The MongoDB Service contains a deliberately incorrect port. Use Lightspeed 2.0.1 Troubleshooting to diagnose the failure, approve a narrowly scoped MCP repair, and verify the change before loading park data. Leave Argo CD, Gitea and other workshop workloads alone.

This is a *25–30-minute, console-first workshop* using *OpenShift Lightspeed 2.0*. The guided walkthrough targets 28 minutes, with up to 2 minutes for transitions.

These timings assume your instructor has already verified image pulls, the Python build, student permissions, Lightspeed MCP read/write tools, tool approval and Argo CD/Gitea isolation. If a prerequisite fails, troubleshoot it separately rather than counting it against the lab. Lightspeed investigates and proposes an approved Service repair; a manual console fallback is available if the AI write path fails.

== Mission 4: Investigate with Lightspeed (4 minutes)

. Open *OpenShift Lightspeed* -> *Troubleshooting*.
+
image::module01-s09k-lightspeed-mode.png[Select Lightspeed Troubleshooting, width=850]
. Paste this prompt:
+
[source,text,subs="attributes+"]
----
In namespace {user}-demo, use resources_get to inspect only these two resources:
1. Service/mongodb-nationalparks
2. Deployment/mongodb-nationalparks

Compare the Service spec.ports[0].targetPort against the MongoDB
containerPort. Report whether the Service is forwarding to the correct port
and identify the smallest necessary fix.

Do not list other Pods or Services. Do not inspect Secrets, execute shell
commands, or change anything.
----
. Review the response. Lightspeed should identify the MongoDB Service port mismatch using live Service and Deployment evidence. Do not accept an unrelated explanation based only on Pod restarts or log connection churn. Do not make any change in Mission 4.
+
[NOTE]
====
This deliberately narrow two-resource query was verified with student `user-clcvz-demo` on 19 November 2026. The earlier broad prompt for Pods, Services and logs repeatedly caused a Qwen3 tool-result safety inspection to reject one result as `data_exfiltration`, while the focused `resources_get` query successfully diagnosed `27018` versus `27017`. A safety alert does *not* mean the Service port is fixed or that a write was attempted. If this focused query also fails, notify the instructor; do not disable the guardrail or widen student RBAC.
====
+
image::module01-s07-lightspeed-root-cause.png[Live Lightspeed 2 diagnosis showing MongoDB Service targetPort 27018 versus Pod containerPort 27017, width=900]

[TIP]
====
*AI check:* Compare the MongoDB Service with the MongoDB Pod. The Service exposes `27017`, but its `targetPort` is `27018`. MongoDB listens on `27017`. The Pod can be Ready even though the Service forwards to the wrong port. Verify the evidence yourself; do not change Secrets or images.

*Checkpoint 4:* Lightspeed identifies that `mongodb-nationalparks` sends traffic to `27018`, but MongoDB listens on `27017`.

== Mission 5: Approve and verify Lightspeed's MongoDB Service repair (3 minutes)

The goal is to have *Lightspeed* perform one approved MCP write, not just describe a command for you to run. A chat message saying "I request approval" is *not* a tool approval. The required approval appears as a separate tool approval request in the Lightspeed interface.

. In the *Showroom Terminal*, check the live fault *before* asking Lightspeed to fix it:
+
[source,bash,subs="attributes+"]
----
oc get svc mongodb-nationalparks -n {user}-demo \
  -o jsonpath='{.spec.ports[0].port}{" -> "}{.spec.ports[0].targetPort}{"\n"}'
----
+
Expected: `27017 -> 27018`. If you see `27017 -> 27017`, the fault is already fixed. If you see `27017 -> mongodb`, this named targetPort also correctly resolves to the MongoDB container's named port; *it is not a broken state*. Do not modify an already-working Service. Ask the instructor to reset the scenario.
. In the *same Lightspeed Troubleshooting conversation* as Mission 4, send the following:
+
[source,text,subs="attributes+"]
----
Your live investigation identified Service/mongodb-nationalparks with
spec.ports[0].targetPort: 27018, while Deployment/mongodb-nationalparks
defines containerPort: 27017.

Prepare an MCP write to repair ONLY Service/mongodb-nationalparks in
namespace {user}-demo. First retrieve the complete live Service manifest.
Using resources_create_or_update, change ONLY spec.ports[0].targetPort
from 27018 to the numeric value 27017, not the named value "mongodb".
Keep all existing Service metadata, labels, annotations, selectors,
cluster IP settings and other port fields unchanged.

Invoke the actual MCP tool-approval workflow and wait for my approval.
Do not treat this chat prompt as approval to execute the change.
Do not modify Secrets, Deployments, other Services or other namespaces.
After the approved write, read the Service again and verify its targetPort.
----
. Examine the proposed `resources_create_or_update` tool call and its manifest. Verify it names *Service/mongodb-nationalparks* in *{user}-demo*, changes only the numeric `targetPort` to `27017`, and preserves every other existing Service setting. *Approve only that exact change.* If Lightspeed merely writes "I request approval" in prose, ask it to *invoke the real MCP tool call for approval*, rather than claiming it has permission. An approval expressed in chat text is not equivalent to the separate tool approval control.
. After approving the correctly scoped tool call, wait for Lightspeed to report the actual update and verification. *Independently verify* in your student terminal:
+
[source,bash,subs="attributes+"]
----
oc get svc mongodb-nationalparks -n {user}-demo \
  -o jsonpath='{.spec.ports[0].port}{" -> "}{.spec.ports[0].targetPort}{"\n"}'
----
+
Expected:
+
[source,text]
----
27017 -> 27017
----
+
The verified Service state proves that a repair was applied. The separate approval interface must also have been observed to claim that *human approval* was tested. No MongoDB Pod restart is required.

[IMPORTANT]
.If Lightspeed cannot execute the repair
====
If the MCP tool is unavailable, the safety classifier rejects a legitimate Kubernetes result, the approval interface does not appear, or the proposed manifest changes unrelated fields, *do not widen RBAC or disable tool-result inspection*. Inform the instructor and take the manual recovery path below. A successful CLI/console patch is a fallback, not proof that Lightspeed executed the change.
====

=== Manual recovery fallback (only if the approved MCP path fails)

. In the console, open *Networking* -> *Services* -> `mongodb-nationalparks` -> *YAML* -> *Edit*. Change **only** `spec.ports[0].targetPort` to the numeric value `27017`, leaving everything else unchanged:
+
[source,yaml]
----
ports:
  - name: mongodb
    port: 27017
    targetPort: 27017
    protocol: TCP
----
+
image::module01-s07a-lightspeed-fix-console.png[Manual fallback: edit only the MongoDB Service targetPort in the OpenShift console, width=850]
+

+
[source,bash,subs="attributes+"]
----
oc patch svc mongodb-nationalparks -n {user}-demo \
  --type=json \
  -p='[{"op":"replace","path":"/spec/ports/0/targetPort","value":27017}]'
----
+
image::module01-s07b-lightspeed-fix-oc.png[Manual fallback: the one-field MongoDB Service patch command, width=850]
+

== Troubleshooting quick reference

[cols="2,3",options="header"]
|===
| Symptom | Check
| Cannot see `{user}-demo` | Sign in as your own student account.
| Python build fails | Open *Builds* -> *Logs* and inspect the error.
| MongoDB Pod not Ready | Check the Secret name, bootstrap ConfigMap and Pod events.
| Backend cannot retrieve data in Mission 3 | Expected. Investigate with Lightspeed before fixing the MongoDB Service.
| Lightspeed cannot inspect resources | Verify namespace and read permissions; notify the instructor if the safety classifier rejects a normal tool response.
| Lightspeed describes approval but never invokes MCP | Ask it to invoke `resources_create_or_update` and use the actual tool approval interface; use the manual fallback if unavailable.
| Backend still cannot connect after Mission 5 | Confirm the MongoDB Service `port` and numeric `targetPort` are both `27017`, and inspect backend logs.
| API returns records but map is blank | Check the `parksmap-discovery` ServiceAccount and the `type=parksmap-backend` label on `Service/nationalparks`.
|===
