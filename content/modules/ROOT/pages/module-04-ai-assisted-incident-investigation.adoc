== Start here: Log in to OpenShift

Open the Showroom *Terminal* tab and authenticate using your assigned workshop credentials *before running any other +oc+ commands*:

[source,bash,subs="attributes+",role=execute]
----
oc login --server={openshift_api_url} --username={user} --password='{password}' --insecure-skip-tls-verify
oc whoami
----

Verify that +oc whoami+ returns {user}. This is a disposable lab environment: the + -p + option can expose your password in shell history and process listings. Do not reuse this password on a personal or production cluster.


Module 3 taught you to measure National Parks workload usage, assess quota headroom, and make or justify a safe GitOps resource-sizing decision. In Modules 4 and 5 we use a *much smaller, independent workload*:
+quay.io/openshift-workshop-applications/weathernow:latest+.

WeatherNow is a simple HTTP web application listening on port 8080. It has *no MongoDB, PVC, image build, credentials or background seed Job*. Your existing National Parks applications remain untouched.

This module uses *your student Gitea repository and a separate Argo CD Application* named +weathernow-lab+ in +{user}-gitops+. You will introduce a controlled readiness mistake, investigate it using Lightspeed and read-only Kubernetes evidence, then repair the source in Gitea.

*Duration: 40 minutes*.

[cols="1,3",options="header"]
|===
| Time | Mission
| 6 min | 1 — Deploy or verify the independent WeatherNow GitOps app
| 8 min | 2 — Break the readiness probe via student Gitea
| 10 min | 3 — Diagnose the stalled rollout with Lightspeed and live evidence
| 10 min | 4 — Validate the readiness diagnosis using Kubernetes evidence
| 6 min | 5 — Restore Git, verify the rollout and compare application health
|===

[IMPORTANT]
.The student and security boundaries
====
* Work only in +{user}-gitops+ and in *your own Gitea main branch*. Leave both National Parks stacks working in +{user}-demo+ and +{user}-gitops+.
* Do not create Namespaces, grant RBAC, read Secrets, change ApprovalPolicy, or install an Agentic Operator.
* No +AgenticRun+ execution or verification stage is used in this workshop. Do not approve automatic remediation; the student repairs Git.
* *AgenticRuns are deferred for students.* No self-service runs or approvals are required; use Lightspeed and namespaced evidence.
====

== Mission 1: Deploy or verify WeatherNow (6 minutes)

. Log in with your assigned identity and select the existing GitOps namespace:
+
[source,bash,subs="attributes+",role=execute]
----
export STUDENT="$(oc whoami)"
export NS="$STUDENT-gitops"
test "$STUDENT" != "system:admin" || { echo "Use your student identity"; exit 1; }
oc get project "$NS"
oc get application national-parks-settings -n "$NS"
----
+
image::module04-s01-weather-student-context.svg[S01: pre-existing student gitops namespace, screenshot placeholder, width=850]

. Set up the WeatherNow source and Application **once**, using the student Gitea fast-forward helper. This operates only on the new +weathernow/+ path and never overwrites an existing WeatherNow manifest:
+
[source,bash,subs="attributes+",role=execute]
----
curl -fsSLo setup-weathernow-gitops.sh \
  https://raw.githubusercontent.com/rhpds/openshift-5-container-workspace/main/scripts/setup-weathernow-gitops.sh

bash setup-weathernow-gitops.sh
----
+
If the script says the WeatherNow files are unavailable upstream, ask your instructor to merge/update the workshop source and your Gitea copy before continuing. This exercise must not edit the Module 2 National Parks Kustomization.
+
image::module04-s02-weather-gitops-setup.svg[S02: student Gitea WeatherNow source and new Application, screenshot placeholder, width=850]

. Verify the second Application and its tiny workload:
+
[source,bash,subs="attributes+",role=execute]
----
oc get application weathernow-lab -n "$NS" -o json | \
  jq '{sync:.status.sync.status, health:.status.health.status, revision:.status.sync.revision}'

oc get deployment,service,route weathernow -n "$NS"
oc rollout status deployment/weathernow -n "$NS" --timeout=120s
export WEATHER_HOST="$(oc get route weathernow -n "$NS" -o jsonpath='{.spec.host}')"
curl -sS -o /dev/null -w 'WeatherNow HTTP %{http_code}\n' "https://$WEATHER_HOST/"
----
+
*Baseline:* +weathernow+ is 1/1 Ready, its Route returns HTTP 200, and +Application/weathernow-lab+ is Synced/Healthy. Container limits are only *200m CPU / 128Mi memory*, leaving shared tenant headroom.
+
image::module04-s03-weather-healthy-baseline.svg[S03: healthy WeatherNow GitOps Application and Route, screenshot placeholder, width=850]

*Checkpoint 1:* WeatherNow works independently of National Parks.

== Mission 2: Commit a deliberate readiness-probe fault (8 minutes)

A new deployment revision is released with a readiness probe aimed at the wrong port. The old version may continue serving HTTP 200 because Kubernetes keeps the previous ready Pod during RollingUpdate.

. Open *Gitea*, sign in as `{user}` with password `{password}` if prompted, then open *your student account → openshift-5-container-workspace → main*. Open:
+
[source,text,role=copypaste]
----
weathernow/weathernow.yaml
----
+
Find the +Deployment/weathernow+ container; its healthy probe is:
+
[source,yaml,role=copypaste]
----
readinessProbe:
  tcpSocket:
    port: http
----
+
image::module04-s04-weather-source.svg[S04: Gitea WeatherNow Deployment source, screenshot placeholder, width=850]

. Change *only the readiness port* to 18080:
+
[source,yaml,role=copypaste]
----
readinessProbe:
  tcpSocket:
    port: 18080
----
+
Do *not* change +containerPort: 8080+, the Service, liveness probe, image or limits.
+
image::module04-s05-weather-bad-probe.svg[S05: WeatherNow incorrect probe port in Gitea editor, screenshot placeholder, width=850]

. Commit to your own Gitea +main+:
+
[source,text,role=copypaste]
----
lab(module04): break WeatherNow readiness for agentic diagnosis
----
+
image::module04-s06-weather-fault-commit.svg[S06: student Gitea fault commit, screenshot placeholder, width=850]

. Watch Auto-Sync without manually patching the Deployment:
+
[source,bash,subs="attributes+",role=execute]
----
oc get application weathernow-lab -n "$NS" -o json | \
  jq '{sync:.status.sync.status, health:.status.health.status, revision:.status.sync.revision}'
oc get deployment weathernow -n "$NS" -o json | \
  jq '{probe:.spec.template.spec.containers[0].readinessProbe, replicas:.status.replicas, ready:.status.readyReplicas, updated:.status.updatedReplicas}'
oc rollout status deployment/weathernow -n "$NS" --timeout=30s \
  || echo "Expected: the new WeatherNow rollout is blocked"
----
+
*Expected:* new Pod +Running+ but +0/1 Ready+; the previous healthy Pod may remain in service. Argo CD can be Synced even though a new revision has not finished rolling out.
+
image::module04-s07-weather-argocd-stalled.svg[S07: GitOps sees new source but WeatherNow rollout is stalled, screenshot placeholder, width=850]
image::module04-s08-weather-pod-readiness.svg[S08: old and new WeatherNow Pods and readiness failure, screenshot placeholder, width=850]

*Checkpoint 2:* The live readinessProbe uses 18080, and the new revision is not ready.

== Mission 3: Ask Lightspeed to investigate (10 minutes)

. In *Lightspeed → Troubleshooting*, enter the following *read-only* request:
+
[source,text,subs="attributes+"]
----
Investigate the stalled Deployment/weathernow rollout in
namespace {user}-gitops. The new Pod is Running but fails
readiness after a student GitOps commit. The older ready Pod
may still serve traffic.

Inspect live Deployment, ReplicaSet, Pod and event evidence, along with available workload metrics and application logs.
Compare the configured readinessProbe.tcpSocket.port with the
container's actual HTTP port and the Service targetPort.
Explain why GitOps can be Synced while rollout is blocked.
Propose the smallest Git source edit. Do NOT read Secrets or
create, patch, scale, delete or execute changes.
Do not inspect other student namespaces.
----
+
image::module04-s09-weather-lightspeed-prompt.svg[S09: Lightspeed WeatherNow investigation prompt, screenshot placeholder, width=850]

. Verify its findings independently:
+
[source,bash,subs="attributes+",role=execute]
----
oc get deployment weathernow -n "$NS" -o json | \
  jq '.spec.template.spec.containers[0] | {ports,readinessProbe,livenessProbe}'
oc get replicaset,pods -n "$NS" -l app=weathernow
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -20
oc get endpoints weathernow -n "$NS"
----
+
. Open *Observe → Dashboards (Perses)* in OpenShift 5. Select *your own* +$NS+ project and the instructor-provisioned *OpenShift 5 | National Parks & WeatherNow* dashboard. Choose a time range spanning the WeatherNow failure; inspect Ready Pods (0 or 1), restarts, CPU and memory. Compare the old Ready Pod with any new unready Pod. A successful query requires a preflighted, tenant-authorized datasource. If it is missing, select *Observe → Metrics* or use +oc adm top+ instead and record the limitation.
+
[source,bash,subs="attributes+",role=execute]
----
oc get persesdashboard workshop-workloads -n "$NS" || echo "Perses workshop dashboard not yet configured; use native metrics."
----
+
[source,bash,subs="attributes+",role=execute]
----
oc adm top pods -n "$NS" --containers || echo "Workload metrics unavailable; use instructor evidence."
oc logs deployment/weathernow -n "$NS" --tail=80 || echo "Application logs unavailable."
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -20
oc get deployment weathernow -n "$NS" -o json | jq   '{ready:.status.readyReplicas,updated:.status.updatedReplicas,available:.status.availableReplicas}'
----
+
*Correlate the signals:* a TCP readiness-probe failure should be visible in Kubernetes Events, while the application might continue logging normally and CPU/memory usage might remain normal. Do not fabricate a stack trace or infer a CPU/memory issue from a failed probe. A trace is not required unless the instructor has separately provisioned a tracing backend and verified WeatherNow instrumentation.

*Optional OpenShift 5 exploration:* On a verified COO 1.6 / Perses / Lightspeed integration, an instructor may demonstrate an AI-assisted dashboard request and inspect the generated PromQL and time range. Students do not need to create dashboards, change datasource access or use AgenticRuns.

If the Route still returns HTTP 200, it is probably the *previous healthy Pod* serving traffic. The key evidence is that the *new* readiness probe targets 18080 instead of +http+ (8080).
+
image::module04-s10-weather-evidence.svg[S10: live probe, replica and event evidence supporting diagnosis, screenshot placeholder, width=850]

image::module04-s16-perses-weather-readiness.svg[S16: WeatherNow readiness and restart panels across incident time window, screenshot placeholder, width=850]

*Checkpoint 3:* You can explain a blocked rolling update using Deployment conditions, Events, logs and actual metrics (or explicitly documented access limitations), without claiming the whole application is down.

== Mission 4: Validate the WeatherNow readiness diagnosis (10 minutes)

[IMPORTANT]
.AgenticRuns temporarily deferred
====
Student-created AgenticRuns are *not part of this workshop* while cross-namespace sandbox lifecycle and tenant isolation remain unresolved. Do *not* create an AgenticRun or AgenticRunApproval, install +oc agentic+, or request additional permissions. Use OpenShift Lightspeed Troubleshooting, namespaced +oc+ evidence and GitOps. A sanitized instructor example may illustrate the lifecycle, but no live AgenticRun is required to complete the lab.
====

Use live Kubernetes and available observability evidence to validate the Lightspeed diagnosis. No student AgenticRun, extra RBAC or approval is required.

. Inspect the readiness probe, serving port, rollout and recent events:
+
[source,bash,subs="attributes+",role=execute]
----
oc get deployment weathernow -n "$NS" -o jsonpath='{.spec.template.spec.containers[0].readinessProbe.tcpSocket.port}{"\n"}'
oc get deployment weathernow -n "$NS" -o jsonpath='{.spec.template.spec.containers[0].ports[0].containerPort}{"\n"}'
oc rollout status deployment/weathernow -n "$NS" --timeout=15s || true
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -15
----
+
. Explain why an unready new replica can coexist with an available old replica. Use your student Gitea copy to identify +port: 18080+ and propose restoring +port: http+.
. Optionally discuss a sanitized instructor AgenticRun example; do not create a run or treat someone else's result as your own evidence.

*Checkpoint 4:* Record the readiness mismatch, rollout status, metric trend, log observation, relevant Event and GitOps recovery plan. Note any genuinely unavailable signals.

== Mission 5: Repair source and verify (6 minutes)

. In student Gitea +main+, restore the original named readiness port:
+
[source,yaml,role=copypaste]
----
readinessProbe:
  tcpSocket:
    port: http
----
+
Commit:
+
[source,text,role=copypaste]
----
fix(module04): restore WeatherNow readiness probe
----
+
image::module04-s14-weather-git-repair.svg[S14: WeatherNow repaired source and Git commit, screenshot placeholder, width=850]

. Confirm Auto-Sync, new Pod readiness, and user response:
+
[source,bash,subs="attributes+",role=execute]
----
oc rollout status deployment/weathernow -n "$NS" --timeout=120s
oc get deployment weathernow -n "$NS"
oc get application weathernow-lab -n "$NS" -o json | \
  jq -r '[.status.sync.status,.status.health.status] | join(" / ")'
curl -sS -o /dev/null -w 'WeatherNow HTTP %{http_code}\n' "https://$WEATHER_HOST/"
oc get deployments -n "$STUDENT-demo"
----
+
image::module04-s15-weather-healthy-recovered.svg[S15: WeatherNow and GitOps healthy after repair, screenshot placeholder, width=850]

*Checkpoint 5:* The WeatherNow deployment is rolled out, Application is Synced/Healthy, browser loads HTTP 200, and National Parks is unchanged.

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Action
| WeatherNow source missing from Gitea | Run the WeatherNow setup helper once after the instructor has published the files; imported student Gitea repositories do not auto-update from upstream
| GitOps Application cannot be created | Confirm you are logged in as +{user}+ and that +{user}-gitops+ exists; do not request cluster-admin rights
| No new Pod after bad commit | Verify live Argo revision, Git path, quota and Deployment events
| Route remains HTTP 200 | Normal RollingUpdate may retain the previous ready Pod; inspect the *new* Pod
| AgenticRun unavailable | Expected during student-run deferral; complete the evidence checkpoint
| Instructor AgenticRun example failed | Use live Kubernetes evidence instead
| Repair commit not applied | Review Argo CD revision and failed operation; do not patch the live Deployment
|===
